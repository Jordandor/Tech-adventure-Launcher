# Tech Adventure Launcher

Windows-лаунчер сборки Minecraft 1.21.1 на NeoForge.

## Возможности

- официальный вход Microsoft через браузер;
- запуск по нику без регистрации;
- однократная установка базовой среды Minecraft 1.21.1 + NeoForge 21.1.235 из отдельного GitHub Release;
- автоматическая установка Java 21 при отсутствии подходящей Java;
- выборочное обновление сборки с GitHub Releases;
- проверка размеров и SHA-256 каждого файла и пакета;
- восстановление повреждённых файлов;
- удаление исключённых из новой версии модов с сохранением резервной копии;
- одноразовая установка авторских настроек, языка, ресурспаков и шейдера;
- сохранение личных настроек, миров, скриншотов, журналов и списка серверов;
- автоматическое подключение к серверу;
- фоновое самообновление лаунчера через отдельные GitHub Releases;
- тихая установка обновлений лаунчера без повторного мастера NSIS.

Заменённые файлы сборки складываются в `.tech-adventure-launcher/replaced` внутри игровой папки.

## Базовая игровая среда

При первой установке лаунчер получает `runtime-manifest.json`, скачивает один проверенный ZIP из `Jordandor/Tech-adventure-Runtime`, проверяет SHA-256 и устанавливает общие каталоги `assets` и `libraries`. Метаданные исходной среды PrismLauncher сохраняются внутри `.tech-adventure-launcher/prism-runtime` и не смешиваются с файлами сборки.

После успешной установки записывается `bootstrap-state.json`. Обычные обновления модов не скачивают runtime повторно: меняются только пакеты сборки. Новый runtime потребуется лишь при смене Minecraft, NeoForge или `runtimeRevision`.

После распаковки лаунчер создаёт собственный стандартный профиль запуска через `@xmcl`. Уже загруженные ресурсы и библиотеки используются повторно; пустые повреждённые файлы удаляются, а недостающие служебные файлы запрашиваются с ограниченной параллельностью и тремя попытками.

## Схема обновления сборки

Сборка не публикуется одним монолитным архивом для каждой версии. Генератор создаёт контентно-адресные пакеты:

- файлы от 2 МиБ публикуются отдельно;
- мелкие файлы стабильно распределяются по 64 ZIP-пакетам;
- манифест каждой новой версии сохраняет URL старых неизменившихся пакетов;
- в новый GitHub Release загружаются только новые пакеты.

Поэтому новая установка получает все актуальные пакеты, а существующая — только те, в которых действительно что-то изменилось. Пользователь может пропустить любое количество версий: текущий манифест всегда описывает полное актуальное состояние.

Файлы с политикой `managed` обновляются лаунчером. Файлы с политикой `seed` устанавливаются только при отсутствии и затем принадлежат игроку. По умолчанию это:

- `options.txt`;
- `config/iris.properties`;
- `config/sodium-options.json`;
- `config/embeddium-options.json`;
- `config/oculus.properties`.

Так при первой установке сразу включаются нужные ресурспаки, шейдер и русский язык, а последующие обновления не сбрасывают выбор игрока.

Манифест сборки никогда не управляет `saves`, `screenshots`, `logs`, `crash-reports`, `servers.dat` и данными аккаунтов. Каталоги `assets` и `libraries` относятся только к отдельной базовой среде. Генератор также исключает служебные `.index`, кеши и идентификатор клиента CustomSkinLoader.

## Репозитории

Используются три публичных репозитория:

- `Jordandor/Tech-adventure-Runtime` — базовая среда и `runtime-manifest.json`;
- `Jordandor/Tech-adventure` — `pack-manifest.json` и пакеты сборки;
- `Jordandor/Tech-adventure-Launcher` — исходники и релизы самого лаунчера.

Разделение обязательно для надёжного самообновления: релиз модпака не должен становиться «последним релизом» приложения.

## Самообновление лаунчера

Установленная версия проверяет GitHub при запуске и каждые четыре часа. Новая версия скачивается в фоне. После загрузки пользователь может перезапустить лаунчер сразу; если он этого не делает, обновление применяется при обычном закрытии.

Основной вариант распространения — NSIS-установщик `Tech-Adventure-Launcher-Setup-...exe`. Portable-версия собирается как резервная. GitHub Release лаунчера должен содержать:

- установщик `.exe`;
- `latest.yml`;
- `.blockmap` для дифференциальной загрузки обновлений;
- при необходимости portable `.exe`.

Workflow `.github/workflows/build.yml` автоматически проверяет и собирает приложение. Тег вида `v0.2.2` создаёт GitHub Release с файлами обновления.

## Разработка

Требуется Node.js 24.

```powershell
npm ci
npm run check
npm start
```

Сборка Windows:

```powershell
npm run dist:win
```

## Публикация новой версии сборки

Подготовь чистую клиентскую папку и запусти:

```powershell
npm run manifest -- `
  --source "D:\Minecraft\TechAdventure" `
  --previous ".\pack-manifest.json" `
  --base-url "https://github.com/Jordandor/Tech-adventure/releases/download/pack-v1.0.1/" `
  --pack-version "1.0.1" `
  --server "example.org:25565" `
  --assets ".\release-assets-1.0.1" `
  --output ".\pack-manifest.next.json" `
  --plan ".\pack-publish-plan.json"
```

Далее:

1. Создать Release с тегом `pack-v1.0.1`.
2. Загрузить только файлы из новой папки `release-assets-1.0.1`.
3. После успешной загрузки заменить `pack-manifest.json` новым манифестом.
4. Не удалять старые Assets, на которые продолжает ссылаться актуальный манифест.

`pack-publish-plan.json` показывает число новых и переиспользованных пакетов. Перед публикацией новая папка `--assets` должна быть пустой.

## Формат манифеста

Актуальный пример находится в `resources/pack-manifest.example.json`.

- `packages` описывает скачиваемые RAW- и ZIP-объекты;
- `files` связывает игровые пути с пакетами и ожидаемыми SHA-256;
- `managed` означает обязательную синхронизацию;
- `seed` означает установку только при отсутствии файла.

Старый манифест схемы 1 поддерживается для плавного перехода, но новые версии следует публиковать только со схемой 2.

## Настройки по умолчанию

`resources/launcher.defaults.json` уже указывает:

- runtime-манифест `Jordandor/Tech-adventure-Runtime`;
- манифест `Jordandor/Tech-adventure`;
- репозиторий обновлений `Jordandor/Tech-adventure-Launcher`;
- Minecraft 1.21.1;
- NeoForge 21.1.235.

Адрес игрового сервера можно задать в манифесте либо в настройках лаунчера. Значение из манифеста имеет приоритет.

## Структура проекта

```text
src/main.js                 основной процесс Electron и автообновление
src/core/auth.js            Microsoft-вход и защищённый кеш
src/core/runtime-bootstrap.js  загрузка и установка базовой среды
src/core/minecraft.js          Java, стандартный профиль Minecraft/NeoForge и запуск
src/core/synchronizer.js    пакетное обновление сборки
src/core/manifest.js        проверка манифеста, URL и безопасных путей
src/renderer/               интерфейс
tools/generate-manifest.mjs генератор контентно-адресных пакетов
test/                       автоматические тесты
```

При публичном распространении модов необходимо учитывать разрешения и условия распространения их авторов.
